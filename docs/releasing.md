# Publishing a signed Neramit Cut update

The application reads `https://github.com/BiG-byt3/Neramit-Cut/releases/latest/download/latest.json`. Each stable release needs a `v<version>` tag and all five assets generated by `tools/release.py`. Uploading source code or an executable alone does not make an online update available.

## Prepare and build

1. Increase the stable `x.y.z` version in both `Cargo.toml` and `installer/Cargo.toml`. Keep the versions identical and commit the updated lockfiles after building.
2. Run the Windows GNU build and tests described in [README.md](../README.md). Build the app before the installer.
3. Write optional UTF-8 release notes to `dist/notes-<version>.txt`: English first, then a line containing `---`, then Thai.
4. Commit and push the reviewed source to GitHub. Note the commit SHA that produced the binaries.

## Sign locally

Install Python and `cryptography`, then run from the repository root:

```powershell
python -m pip install cryptography
python tools/release.py sign
python tools/release.py verify
```

The existing ECDSA P-256 private key is read from `%USERPROFILE%/.neramit-release/update-signing-key.pem`, or the path in `NERAMIT_RELEASE_KEY`. Keep that private key outside the repository and keep a secure backup. Do not regenerate or change it for later releases: installed copies trust the public key already embedded in `src/update.rs`. The signing command refuses a key that does not match that public key.

The script creates `dist/<version>/` containing:

- `NeramitCut-Setup-<version>.exe`
- `NeramitCut-<version>.exe`
- `latest.json`
- `SHA256SUMS.txt`
- `release-notes.txt`

The manifest signs `NeramitCut|<version>|<installer-sha256>` and `NeramitCutPortable|<version>|<portable-sha256>` with separate product domains. This update signature is distinct from Windows Authenticode signing.

## Publish

### Publish through GitHub Actions

The `Publish signed update` workflow accepts only the branch `release/v<version>` matching both Cargo manifests. Sign and verify the package locally first. The private key stays on the signing computer; GitHub Actions verifies the committed package with the public key, then uploads the exact files without rebuilding them.

After the source changes are committed on `main`, create a package branch. Replace `1.2.3` with the version in both manifests:

```powershell
git switch main
git switch -c release/v1.2.3
python tools/release.py verify
git add -f dist/1.2.3
git commit -m "Package signed Neramit Cut 1.2.3 update"
git push -u origin release/v1.2.3
```

Stop if verification fails. Push triggers `.github/workflows/publish-signed.yml`, which checks the branch/version match, verifies both executables, hashes and signatures, and runs the existing draft-then-publish script with the workflow's repository-scoped `GITHUB_TOKEN`. The tag points at the package commit. The workflow can also be started manually from the matching release branch; selecting `main` fails the branch check. Already published versions are refused.

Keep signed binaries on these package branches; do not merge their `dist/` files into `main`. The source branch remains free of build outputs. Check the Actions run and the published release before announcing the update.

### Publish directly from the signing computer

Provide `GITHUB_TOKEN` through your local secret manager or environment, with repository Contents read/write access. Never put a token in source code or a command committed to Git. Set the intended source commit, then publish:

```powershell
$env:NERAMIT_RELEASE_TARGET = (git rev-parse HEAD).Trim()
python tools/release.py publish
```

The script verifies the package, creates or resumes a draft, uploads all five assets, checks their uploaded sizes, then publishes it as the latest release. It refuses to overwrite an already published version. If publication fails, correct the issue and rerun the command; the draft can be resumed.

Alternatively create a draft in the GitHub Releases UI using tag `v<version>` at the source commit, upload the five files unchanged, and publish only after every upload completes. Select a stable release and mark it latest.

## Verify the online release

From PowerShell, run the published portable executable with release diagnostics:

```powershell
$check = Start-Process -FilePath '.\target\release\NeramitCut.exe' -ArgumentList '--check-update', '--download' -Wait -PassThru -WindowStyle Hidden -RedirectStandardOutput '.\update-check.json' -RedirectStandardError '.\update-check-error.txt'
Get-Content '.\update-check.json'
if ($check.ExitCode -ne 0) { throw 'Online update verification failed' }
```

The JSON should report `signature_verified: true` and both executable names in `verified_assets`. These diagnostics download and validate the release without installing it. An older supported version should report `newer_available: true`; the released version reports `false`. Also check the update dialog in the application. CI artifacts alone cannot be used as signed online updates.
